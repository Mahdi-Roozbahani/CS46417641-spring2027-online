# Team Project

<a href="../../../../../files/team-project-starter.md" download="team-project-starter.md">Download the complete Markdown starter (.md)</a>

Open the downloaded file in a text editor and replace the instructions with your own work. If your browser displays the file instead of downloading it, save the page as a `.md` file.

This is a starting layout for **your team's own project website**, not a topic or result to copy. Keep the main headings so your TA can find the required work. Your team **may add subsections, better explanations, interactive features, and a different visual design**. Use this same website for the proposal, midterm review, and final. At proposal, write what you plan; at midterm, show what you have done; at final, revise it to show completed work. The team chooses a feasible question and lawful dataset, unlike the individual assignment where the course supplies the data.

## 1. Introduction and related work

### 1.1 What question are we trying to answer?

State one specific question, why it matters, and what would count as a useful answer. Say when the question changes and why.

### 1.2 What have others already done?

Describe a few relevant sources you actually read and what your project will test, compare, or build beyond them. You do not need to claim a new research discovery.

## 2. Problem definition and data

### 2.1 Which data did we choose, and can we use them?

Give the dataset name, a link to where the team obtained it when possible, the number of examples, the information each example contains, and whether answers (labels) are known. State any license, privacy, or sharing restriction that applies. If the first dataset was unavailable, explain the change.

### 2.2 How did we prepare and divide the data?

Explain what the team cleaned or changed. State which examples were used to train methods, which helped choose settings, and which were saved for final testing. Explain how you kept test information out of training.

## 3. Methods and baseline

### 3.1 What simple result are we trying to beat?

Name the simple baseline you will compare against and show its actual result by midterm or final. Compare it with methods addressing the same question.

### 3.2 What other methods did we try?

For each method, explain why you chose it and whether it is **planned**, **in progress**, or **completed**. At proposal, name at least three methods or models you plan to test; results are not required yet. By final, run and report at least three different methods or models in total. A baseline counts only when actually run and compared. CS 4641 must include a supervised model; CS 7641 must include supervised and unsupervised methods. See the [course project requirements](https://mahdi-roozbahani.github.io/CS46417641-spring2027-online/docs/grading/project-breakdown/team-project/final/) for details.

## 4. Evaluation and results

### 4.1 What did each method produce?

Show real numbers, tables, or figures and explain what they mean. At proposal, write what you plan to measure. At midterm, show your first results, even when weak. At final, show the completed results. Methods answering different questions should not be forced into one comparison: for example, a prediction model and a grouping method need different explanations and may need different measures.

### 4.2 Required interactive visualization

Include **at least one useful interactive visualization** of the team's own data or model results by the final deadline. A reader should be able to change something—such as a filter, class, feature, threshold, or model setting—and see a relevant chart or result change. JavaScript is one way to build this. Explain what the interaction helps the reader understand. A static image or decorative animation alone does not meet this requirement.

## 5. Discussion and limitations

Compare results that answer the same question. Explain at least one success, one failure or surprising case, and an important tradeoff. Describe data gaps, possible bias, uncertainty, privacy concerns, and other limits that affect how someone should interpret or use the result. Say what the team observed separately from what it guesses.

## 6. Conclusion and next steps

Answer the question from Section 1 as far as the evidence allows. Name one next experiment that would be worth doing.

## 7. Project plan and member contributions

Include a Gantt chart or simple timeline showing milestones and who owns them. At each checkpoint, update it to show what actually happened. Name each member's work and next responsibility; all members must understand the whole project.

## 8. References and AI-use disclosure

Cite sources the team actually used. If generative AI helped, name the tool, purpose, scope, and what the team verified under the course policy. If none was used, say so.

## Optional bonus work (not required)

The required interactive visualization is **not bonus work**. If your team requests bonus credit, list the specific bonus items completed, show the evidence, and identify who did each item. See the **Optional Team-Project Bonus** page on the course website for the five checkable items and their limits. Bonus credit is not automatic.
